## 第二轮复审后的实现证据

用户确认下一波怪刷出时若圈内超限即判负。原型在下一波首批入场后立即按圈内容怪点数判定，计入该时点刷在圈内的怪；等于上限可继续。同波后续批次不触发检查。固定编号随快照恢复，出怪身份不重复。第 1 帧清除旧怪时，第 2 帧检查为 1/1，最终第 8 帧胜利；保留旧怪时，第 2 帧检查为 2/1，当帧失败。

| 项目 | 已运行的最小集成证据 |
| --- | --- |
| R1 | 实际帧循环执行同帧购买及合成，覆盖库存争用、材料争用、重复指令，以及提交前后快照重放。验证只产生一件装备，金币和随机数符合预期。 |
| R2 | 小配置在主线完成后保存胜利等待，继承装备、金币、随机状态及攻击冷却进入无尽。完成第 5 波后在第 6 波首批出怪时失败，记录最后完成第 5 波。重复进入、终态恢复及重开有断言。 |
| R3 | 实际帧循环覆盖跨波检查、同波分批、圈外怪、不同点数、稳定 ID 和冷却到期。固定输入对照 1×、4×、中途改速、暂停、分段补算与恢复。Chrome 跑了 1×、4×、模拟补算和第 1 帧普通 URL 刷新，完整事件与最终快照一致。 |
| R4 | Chrome 在真实 IndexedDB 事务的写请求成功后注入中止，验证回滚旧快照、合并待写请求、失败后的新写入，以及波中、终态和重开交接。 |

复现入口见 [原型运行说明](../prototypes/first-battle/README.md)。本次实现的是最小复审原型，经济探针覆盖购买与合成，采用简化的无尽内容配置。正式玩法、完整阶段 UI、代表性大快照性能及移动端按已有 M1 和后续适配安排处理。本批证据已由上文第三轮复审核对。

**本轮实际运行。** Node v24.22.1 调用仓库现有 `battle.ts`：1×、4×、分块补算、内存克隆恢复的完整状态仍相同，均在第 8 帧胜利；取消第 3 帧攻击仍在第 3 帧失败。保持该正例，仅追加第 3 帧出怪事件，得到以下对照：

| --- | --- | --- |
| 第 3 帧击杀旧敌人后的容怪 | 第 2 帧出生的敌人计 1 点；第 3 帧新怪暂计 0 点；1/1，继续运行 | 使用 `units.length` 得到 2/1，当帧失败 |

复现输入沿用文末探针的 `consecutive` 场景：`newBattle()` 后追加 `{ frame: 3, type: 'spawn' }`，调用 `advanceFrame` 三次。文末断言保留首轮旧实现的观察值；下一版回归应按本节的新期望更新，不能把“成功复现旧失败”报告成“新规则通过”。本次没有修改原型来制造通过结果。不同容怪点数的独立算例能说明规则含义，但尚未覆盖真正帧循环里的出怪、击杀、检查、快照与恢复。

**证据范围。** 本轮未重做浏览器 3D 和 IndexedDB 实测；已有桌面贴图／动画／选中与单次提交续局的证据继续引用。内存克隆恢复仅证明该样本的逻辑可重放，不能证明写入失败后的恢复。仓库中的原地图规则核查脚本不是当前原创对局引擎的集成测试。

**下一次复审需要提交的最小证据包：**

1. R1：可执行的购买／合成事务探针，记录竞争、重复命令、拒绝不扣费／不推进随机数、提交前后恢复的输入和输出。
2. R2：使用小规模测试配置跑通主线胜利等待→继承状态进入无尽→完成 5 波→第 6 波失败→恢复终态→重开，逐点对照装备、资源、冷却、事件及波次。
3. R3：让实际帧循环符合逐批宽限和唯一 ID，保持原正反例，再接入不同容怪点数、冷却结束击杀、改速／暂停、分块补算与恢复对照。
4. R4：通过实际保存协调器和 IndexedDB 注入失败／中止，覆盖 A 成功后 B 失败恢复 A、A 在写时 B/C 合并、失败后 D 可再保存，以及普通刷新、切模式和旧写入未结束时重开的交接。

这些证据可以合用一个最小集成原型，复用同一命令入口、帧循环和保存协调器。纯粹在另一个脚本里重新实现规则，只能作为参考模型；需将其期望与被评审代码比较，才可关闭集成条件。无需在此阶段补齐最终内容、美术或无尽高负载优化。

另在提交探针时统一两处文字边界：R1 的“按目标帧和序号处理”与 R3 的“按帧、阶段、序号”应明确适用的命令类别（例如先发攻击、后发升级同帧时，攻击使用哪一档属性）；R2 的“清理主线剩余事件”应限定事件归属，说明持续技能／装备效果的事件如何跟随继承状态。它们归入现有 R1–R3 验证用例，不新增范围或另立门禁。

**门禁处理。** 保留 G4「设计完成」，G5 暂不通过，G6 未进入。本轮结论是“修订方向接受、核心验证未关闭”，不是技术选型被否决。V1 无尽高负载＋4×＋自动存档仍在 M1 验收前，V2 完整桌面素材在 M1，V3 手机适配在后续里程碑；已验证的桌面行为不重复设门槛。需求基线 v1.0 维持原范围。

## 首轮阻塞项与关闭条件

### R1：局内操作必须由玩法层一次性提交

**证据与影响。** P3 只有“玩家操作生效后保存”，没有定义建造、升级、抽卡、购买、合成的执行者、费用与产物的提交边界。原型 `battle.ts:7` 的指令只有目标和逻辑帧，`enqueueAttack` 只排攻击；`main.ts:126` 在指令入队后保存。若直接扩展 UI 回调扣费、异步加载模型后建塔，可能出现扣费无塔、双次抽卡、合成材料已消耗而产物未生成，无法证明正常游玩和续局用例。

**P3 修订交付物。** 一张命令契约表：五种操作的输入、合法阶段、目标帧及同帧序号、前置校验、状态写入、失败结果和保存触发点。建议由唯一的对局状态持有者在逻辑帧内校验并原子提交，UI 只提交意图，3D 加载不参与事务。

- 建造：位置／占位／资源等前置条件通过后，扣费和塔实例创建一同生效。
- 升级：费用、等级、属性及对冷却的影响在同一边界处理。
- 抽卡：支付、随机状态推进、卡片归属一同生效；同一命令重试不得再次抽取。
- 购买：价格、库存、资源、物品归属一同更新。
- 合成：按物品实例校验材料、费用和产物位置；材料消耗与产物生成同成同败。

**复审通过条件。** 为五种操作给出成功和失败前后状态例子；给出同帧连续购买／合成争用同一资源、重复提交同一命令、提交前后刷新三个边界的期望结果。结果必须是一次合法提交或完全拒绝，无负资源、重复物品或半成品状态。补一个购买→合成的最小事务探针，验证固定种子／操作时刻下连续运行与恢复一致。具体价格、卡池和配方数值可以留给内容配置任务，事务语义不能留空。

### R2：主线与无尽需要同一对局的生命周期契约

**证据与影响。** 需求已规定胜利后进入无尽且继承本局数据，但 P3 未指定模式切换负责人。`battle.ts:15,29,76` 只有 running／win／loss，敌人和事件清空就胜利，胜利后不能推进；`main.ts:42` 的 reset 创建新样本。若将这条终止路径直接用于主线，无尽无法继续；若用重开进入无尽，会重置阵容和资源。当前也没有当前无尽波次、最后完成波次及无限生成规则。

**P3 修订交付物。** 由对局控制模块（可命名 `RunSession`，属于建议）唯一持有阶段与模式，波次调度器仅报告波次完成。给出“开局→主线→主线胜利结算→进入无尽→无尽失败→重开”的状态图，以及每条边的触发、原子写入和保存点。主线胜利是进入无尽前的可恢复阶段，不能直接等价于整局不可继续。

继承表须覆盖塔实例与位置／等级、技能及剩余冷却、装备实例与归属、背包／卡片、资源、随机状态；商店库存和未执行命令也须明确保留或结束规则。无尽开始只初始化该模式确需的新状态；重复点击进入、恢复后再次进入均只生效一次。波次配置／生成器须定义出怪完成与清场的关系、强度成长、当前波次和最后完成波次的更新点、未来事件与全局唯一单位 ID。按需生成后续波次，不以 5 波样本作为终点。

**复审通过条件。** 用带升级、装备、剩余资源和未结束冷却的主线终态，演算进入无尽前后及两侧刷新后的状态；继承项一致、入场只发生一次。最小生命周期探针跑过至少 5 波并进入第 6 波，逐波记录出怪和成长；在第 6 波中途失败时结算最后完成第 5 波，之后不再出怪。重开生成新局身份与初态，旧事件／旧保存不能污染新局。该探针可用小规模配置，不要求先完成全部美术和约 10 分钟内容。

### R3：把原样本顺序扩展成完整逻辑帧与时钟规则

**证据与影响。** 当前每帧实际顺序是移动→本帧出怪→玩家攻击与击杀→到期容怪检查→胜利检查（`battle.ts:29–79`），固定步长 250 ms。P3 明确了出怪后下一帧的击杀／检查顺序，但没定义旧检查与新出怪重合时的规则，也未包含自动攻击、技能冷却及局内事务。

本次仅给样本追加 `{frame: 3, type: 'spawn'}`，就得到第 3 帧“出怪 3/1→击杀 old→检查 2/1→失败”；第 3 帧刚出生的敌人也参与旧检查。这揭示“每批新怪都有一帧处理机会”与“到期检查汇总当时全部活怪”在连续出怪时存在差异，**当前文字和单次出怪证据未消除该歧义**，不能擅自把其中一种记作已批准规则。样本还把两个新敌人都命名为 `new`，无法用于多波目标、选中与存档身份。

**P3 修订交付物。** 写出每一帧的唯一阶段顺序，涵盖命令提交、移动、冷却、自动攻击／技能／伤害和死亡、出怪、容怪、波次及结算、帧末快照；规定同帧事件稳定排序和新事件可进入的最早阶段。明确相邻批次的检查是否涵盖当帧新怪、多个检查如何合并、不同容怪点数如何求和，保持已确认样本不变。命令、单位、事件采用可恢复的唯一身份／顺序，不能沿用 `old/new` 或用怪物只数代替容怪点数。

时钟只产生待推进的固定逻辑帧，统一调用战斗更新。定义暂停前余量、改速时旧时间按旧速度结清、新输入对应的逻辑时刻，以及补算时输入如何排队，避免回填到已经过去的帧。长补算可以分批让出执行，但不得丢弃未算帧或让渲染决定战斗；若中途失败／进入主线胜利结算，明确停点与剩余时间的处理。恢复时以快照逻辑时间和新现实时间锚点启动，不将关闭间隔补入对局。

**复审通过条件。** 保留既有正反例，再补相邻两帧出怪、冷却恰好结束并击杀、同帧多命令和不同容怪点数案例，给出逐帧期望日志。固定输入时刻，比较 1×、4×、中途改速、暂停恢复、任意分块补算和快照恢复，玩法状态与事件顺序完全一致。冻结中的 4× 补算和关闭后不补算沿用 ADR 0002；补算导致失败时必须停在失败帧。连续出怪歧义需在 P3 明确，不以性能实测替代规则决定。

### R4：完整快照与保存协调必须覆盖启动、失败及换局

**证据与影响。** P3 已要求波次、单位、资源、装备、冷却、随机状态和待处理事件，方向正确。但 `Snapshot` 只有 `Battle + remainderMs`；其中塔是静态常量，单位数组只有敌人，没有模式／波次、装备、冷却、商店等状态。当前证据证明的是第 2 帧的容怪检查恢复，不能证明有技能冷却和无尽待出怪事件的恢复。

`save.ts:10–18` 在调用时克隆并以单笔事务覆盖 `current`，以 transaction complete 为成功点，支持保留“整帧快照”方案。重叠对象存储的读写事务按创建顺序访问，事务失败回滚；**不能仅因异步就断言这里已经存在写入乱序或半份存档**。[IndexedDB 事务生命周期与调度](https://w3c.github.io/IndexedDB/#transaction-lifecycle)

真正未闭合的是应用层协调：P3 的“在写一份＋只保留最新待写一份”尚无完整生命周期契约；原型每次调用都直接克隆并开事务。`main.ts:151–160` 只在 URL 有 `resume` 时恢复且启动为 1×，普通刷新／重新打开不自动读档；reset 也没有持久化新局。因此不能把专用刷新按钮的成功推广为普通续局、失败结算后刷新或重开后刷新已通过。

**P3 修订交付物。** 一份快照字段／恢复责任表和保存状态机，至少明确：

| 状态组 | 必须可恢复的信息 |
| --- | --- |
| 身份与兼容 | 存档格式及配置版本、对局身份、保存修订号；不兼容时明确失败，不能静默覆盖已有存档 |
| 阶段与波次 | 主线／无尽模式、胜利等待／运行／失败阶段、当前波次、最后完成波次、成长参数或其确定性推导依据 |
| 战场与经济 | 己方塔和敌人的稳定 ID、位置、生命及其他会影响下一帧的单位状态；等级、卡片、资源、库存、装备实例与归属 |
| 技能与事件 | 冷却／攻击计时，首个里程碑实际采用的持续效果；待出怪、容怪及伤害事件的帧与顺序；生成进度、下一 ID 和随机状态 |
| 命令与时钟 | 已接收未执行命令、去重／顺序状态、已完整结算的逻辑帧、时间余量、倍速、暂停状态及补算剩余量的恢复规则 |

待出怪队列与波次生成进度之间必须指定唯一恢复依据；恢复不能既重播已经出过的波次，又装载同一批待出怪事件。存档在完整帧边界捕获；同帧命令若已入队而尚未执行，须明确包含它们的边界。保存请求和保存成功是两回事，只有事务完成才能更新“最近成功保存”标记；失败保持旧快照并释放写入状态，继续处理最新待写项。

普通启动先读取快照，再允许新局写入。模式切换／结算／重开与保存协调器共享对局身份和修订顺序，取消未开始的旧局待写项，隔离旧回调；已在写的事务需有明确串行交接策略。新局尚未成功保存就刷新时，应明确恢复的仍是最近一次成功提交，不能报告“新局已保存”。活页面冻结与页面回收是不同生命周期；浏览器回收时不能依赖最后一个回调补救保存。[Chrome 页面生命周期](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)

**复审通过条件。** 补 IndexedDB 小规模故障探针：A 保存成功后 B 写入失败，刷新恢复 A；A 在写时连续请求 B、C，仅保留最新待写 C，最终恢复 C；C 失败则恢复最近实际完成的事务，并验证后续 D 可成功。覆盖事务 abort／写入错误及提交前关闭，存档不能处于半更新状态。另在有冷却、场上敌人、无尽待出怪事件和未执行命令时保存，普通刷新后逐帧对照连续运行，事件不重复、不丢失，资源／装备一致。覆盖主线转无尽和重开时旧写入未完成的路径；停留在失败结算后刷新仍保持结算且不再出怪。

## 首轮逻辑探针（历史）

以下脚本和输出仅对应第二轮记录哈希所指的旧实现，保留用于解释原发现。当前规则和 API 已更新，请使用 README 中的 `check:battle` 与 `checks/storage.html`，不要对当前源码执行下方旧断言来判断是否通过。

本次实际执行并通过的断言：原样本 1×、4×、分块补算和内存克隆恢复的完整对象相同，第 8 帧胜利；无第 3 帧攻击的反例在第 3 帧失败。追加连续出怪后，第 3 帧失败且两个活敌人 ID 均为 `new`。这个追加样本是扩展边界的证据，不是对已通过原样本的否定。

从仓库根目录，用支持 TypeScript 类型剥离的 Node 重现：

```sh
node --input-type=module <<'JS'
import assert from 'node:assert/strict';
import { advanceTime, advanceFrame, newBattle } from './prototypes/first-battle/battle.ts';
const init = () => ({ battle: newBattle(), remainderMs: 0 });
const normal = init();
for (let i = 0; i < 8; i++) advanceTime(normal, 250, 1);
const fast = init(); advanceTime(fast, 500, 4);
const background = init();
advanceTime(background, 500, 1); advanceTime(background, 1500, 1);
let restored = init(); advanceTime(restored, 500, 1);
restored = structuredClone(restored); advanceTime(restored, 1500, 1);
for (const value of [fast, background, restored]) assert.deepEqual(value, normal);
assert.equal(normal.battle.frame, 8); assert.equal(normal.battle.result, 'win');
const loss = { battle: newBattle(false), remainderMs: 0 };
advanceTime(loss, 2000, 1);
assert.equal(loss.battle.frame, 3); assert.equal(loss.battle.result, 'loss');
const consecutive = newBattle();
consecutive.pending.push({ frame: 3, type: 'spawn' });
for (let i = 0; i < 3; i++) advanceFrame(consecutive);
assert.equal(consecutive.result, 'loss');
assert.deepEqual(consecutive.units.map(unit => unit.id), ['new', 'new']);
console.log(consecutive.log.join('\n'));
JS
```
