先展开完整可达依赖并检查排除项冲突，再确定小批次顺序。英雄与神杖、形态或召唤有相互依赖时合并为一个可验收批次；共享机制先修，再接依赖对象。M3-15 从首个内容批次即参与，不能等全部英雄完成后才开始入口实现，也不能要求未接入口的对象提前通过正常取得验收。

当前 `tools/check-m2-configuration.py` 固定断言 19 张卡和四名开局，`checks/m2-normal-run.mjs` 默认选 i564。基础批次需新增或适配 M3 配置、覆盖生成、正常局策略、浏览器及存档夹具检查，明确每条命令对应的版本；保留旧断言作为 M2 历史检查，不删除规则断言来换取通过。开发期区分“目标配置完整”和“当前已开放内容可运行”，未开放项持续显示未实现／待集成；最终候选必须全部达到本期目标。

### 活动积分与礼盒取得闭环

M3-11 先核活动积分来源，M3-15 负责实现。已有线索见 [平台入口](rules/platform-and-access.md)与 [礼盒规则](rules/event-boxes.md)：原脚本 m501/m502/m503 死亡奖励分别出现 30–120、100–260、240–400 活动积分，但仍须核完整生成入口、普通主线可达性、归属、随机调用和重复奖励条件；不能仅凭死亡回调认定入口已开放。其他活动结算／任务来源逐项核定是否属于本期，不据此恢复整个历史活动系统。

来源表须列出采用／排除原因、成本、奖励、次数、跨局字段和证据，保证本期至少有一条从零余额赚取并购买礼盒的真实路径。若来源实际依赖排除模式且现有证据无法支持本期入口，立即记录具体范围冲突，只暂停相关入口，继续其余任务；不得临时赠送积分、改用普通积分或用受控注资代替正常取得。礼盒仍按已决永久全开后的实际分支验收；原版未拥有奖池留作规则对照，不要求正式账号触发不可达分支。

### 正常流程预演与失败处理

正常流程脚本随内容接入推进，不等最终冻结才编写。开局候选来自已保存的实际随机结果；提前登记候选选择顺序、无偏好英雄时的策略、抽卡／经营／突破操作。保留原五种子 14、47、811、1709、20261124 及所有结果；策略调整另记版本和原因，不覆盖失败记录。

为 A11 护符、A18 三把妖刀两路、SSR 正常取得、13 条资格链及礼盒分别登记目标、种子／初始档案、操作策略、终止条件和缺失证据。稀有结果可按预登记顺序增加正常样本，保存全部成败，不读取未来随机结果操纵路线，不重开刷开局，不以受控测试替代正常获取。受控测试用于验证等级、边界、故障和复杂组合。

首次可运行批次即开始相关预演；完整卡池、候选及战斗效果齐备后，先跑原五种子，再冻结最终候选复验。历史 478.184361 秒击杀仅作参考，不保证扩池后满足 480 秒。失败先区分实现偏差、脚本操作缺口和规则下的可达性：前两项直接修复并重验；若需要改变已决经济、概率或通过线，提供具体失败轨迹及原因后再提出决策，不能自行降低标准。单项失败不阻塞无关工作，未关闭项始终保留。

### 性能提前验证与最终复验

性能沿 [M2 固定环境与通过线](m2-configuration.md#固定峰值场景与提前验证)，不因扩池自动放宽。M3-11 核实指定机器、Chrome 版本、硬件加速、视口及采样工具可用；环境变化建立单独基线，不能混入旧环境成绩或直接宣称满足原合同。

- 第一次：公共连续接触修复后，在当前真实场景试跑 PF01/PF02 和当时最大 PF03，确认输入、帧耗时、事件积压、复制／序列化／提交的测量链可用。
- 第二次：代表性新增复杂英雄及装备接入后，按实际召唤、幻象、持续效果和模型负载补充场景。保留旧 PF02 对照，新增负载若更高则另建有版本和摘要的场景；PF03 从新轨迹重新选峰值。
- 最终：同一完整候选在指定环境完成 PF01–PF03、存档开／关各三次 4× 现实十分钟、冻结补算及冷启动，并完成公开 HTTPS 验证。短峰值与持续样本分开，不能混入终态空闲帧。

前两次使用本地或内部候选，不发布分批试玩；失败明确归属战斗、渲染或保存任务，涉及公共机制的问题在继续扩大同类负载前处理。高负载整局与性能采样错开，避免相互干扰。开发期运行类型检查及直接相关的行为／浏览器测试，阶段集成运行 `npm run check`；最终冻结后的失败修复更新构建摘要，并复验失败项和受影响范围，不无差别重跑全部历史检查。
