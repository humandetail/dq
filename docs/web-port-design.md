### 首个可玩里程碑

用户已确认首个里程碑包含桌面短主线和无尽模式。短主线采用一张原创地图、一个难度，目标局长约 10 分钟。已确认以下三组验收用例。

| 用例 | 通过条件 |
| --- | --- |
| 正常游玩 | 从开局按正常流程完成建造、升级、抽卡、购买和合成，到达主线胜利结算。参战单位能显示贴图并播放攻击动画。 |
| 失败与重开 | 下一波首批入场后，圈内容怪点数超限时立即触发失败结算，重开后回到新局初态；判定口径见 C01。 |
| 时间与续局 | 固定初态、随机种子和操作的对局时刻，1×、4× 和后台补算得到相同的结算结果。在有技能冷却和待出怪事件时刷新，确认续局与连续运行结果一致。 |

无尽模式从短主线胜利结算进入，沿用本局阵容、装备和剩余资源。用固定阵容连续完成至少 5 波，逐波核对出怪和强度成长。波次进行中刷新，须恢复当前波次、场上敌人和待出怪事件。继续对局直至容怪点数超限，结算记录最后完成的波次并停止出怪。5 波为验收样本，无尽持续至失败。

深渊、多档难度和手机触控在后续阶段验收。

先用一座原创塔和一种敌人搭建可运行场景，验证以下两项，再扩充首个里程碑的内容。

## P3 架构设计

### 容怪判定时序

用户补充确认，**下一波怪刷出时才检查圈内容怪**。首批出怪加入战场后，立即汇总圈内仍存活敌人的容怪点数，包含该波刚刷入圈内的敌人。超过上限立即判负，等于上限继续。圈外怪和同一波后续批次各自按所在位置与所属波次处理，后续批次本身不触发判负。该规则替代早期的出怪后下一帧检查。

### 自动存档与离开确认

2026-11-24 确认，刷新或重新打开游戏时直接恢复最近一次成功写入的本机对局快照。快照记录当前逻辑帧、波次、场上单位、资源、装备、技能冷却、随机状态和待处理事件。按 C01，首批出怪与随后的同帧容怪检查一起结算，不能在两者之间捕获快照。帧末快照恢复后从下一帧继续处理尚未到期的出怪等事件；模式切换则在完整阶段边界捕获快照。

玩家在对局期间尝试刷新、关闭标签页或导航离开时，请求浏览器显示原生确认。浏览器决定是否显示提示和提示文案。自动存档独立于离开确认运行，提示不可用时仍可从最近一次成功写入的快照续局。[HTML 标准](https://html.spec.whatwg.org/multipage/browsing-the-web.html#event-beforeunload)

首版在建造、购买、合成等玩家操作生效后请求保存，战斗期间每 5 秒现实时间请求保存，页面转入后台时额外尝试一次。用 IndexedDB 异步写入，只保存恢复对局所需的数据。同一逻辑帧内的请求可合并，前一次写入未完成时仅保留最新的待写快照。写入失败时仍可恢复上一次成功提交的快照。[IndexedDB 规范](https://w3c.github.io/IndexedDB/#dom-idbobjectstore-put)

首版存档频率以性能验证为准。无尽模式可运行后，用同一高负载场景比较启用与禁用自动存档时的帧耗时和输入响应，覆盖 4× 倍速及连续玩家操作，检查生成、复制和提交快照时是否出现可感知卡顿。[IndexedDB 性能实践](https://web.dev/articles/indexeddb-best-practices-app-state)

### 战场判定与 3D 表现

2026-11-24 确认，塔的射程和单位碰撞使用战场平面坐标及玩法定义的范围。3D 场景负责显示模型、播放动画和鼠标选中，并把选中的单位交给玩法逻辑处理。在一座塔与一种敌人的验证场景中，检查敌人进出射程和碰撞范围时的结果，并更换模型或播放动画，确认相同的战场状态得到相同的玩法判定。

### 原创内容配置

2026-11-24 确认，首版在源码仓库维护原创塔、敌人和波次的配置。塔配置包括射程和攻速，敌人配置包括生命和移动速度，波次配置包括出怪时间、敌人种类和数量。对局逻辑读取配置执行规则，调整这些数值只需修改对应配置。

### 首个验证场景的技术栈

2026-11-24 确认，使用 TypeScript 编写对局逻辑，Vite 构建，HTML 和 CSS 提供验证页操作与状态面板。3D 首选验证路线为通过 `war3-model` 直接加载 MDX 模型与 BLP 贴图。首个本地验证场景使用用户提供的「四糸乃」，检查贴图、队伍光晕、待机与攻击动画切换以及鼠标选中。通过后加入一个敌人模型，验证同屏交战。正式 3D 选型以浏览器验证结果为准。早期静态清点提供了模型格式与缺失依赖的证据。[模型资源清点](rules/model-asset-inventory.md)

用户提供「四糸乃」作为参考样本。`war3-model` 4.0.1 已成功解析 `Yoshino.MDx`（版本 800，8 个网格组，10 段动画），并成功解码目录内两张 BLP1 贴图。模型另引用 `ReplaceableId 2` 队伍光晕。该样本可用于评估浏览器直接加载路线，实际画面、动画播放和鼠标选中仍待验证。[war3-model](https://github.com/4eb0da/war3-model)

### 首个验证场景

原型使用一座原创哨塔和一种敌人。四糸乃通过本地文件选择器加载，作为哨塔的显示模型。几何模型用于显示敌人，也用作哨塔替换模型，便于比较同一战场状态下的判定。

| 模块 | 交接数据与职责 |
| --- | --- |
| 战斗 | 接收指定逻辑帧的玩家指令，推进固定步长的逻辑帧。维护单位位置、生命、随机状态和待处理事件，统一判定射程、碰撞和胜负。 |
| 存档 | 在一帧完整结算后，通过一笔 IndexedDB 事务保存该帧的对局状态、随机状态、待处理事件和时钟余量。续局时将整份快照交回战斗模块，再从下一帧推进。 |
| 3D | 读取该帧的塔与敌人位置以及攻击结果，用于模型定位和动画。鼠标命中显示模型对应的区域后，将单位 ID 交给玩法层。模型替换和动画只更新表现状态。 |

验证用例固定初态和种子。第 1 帧清掉旧怪，第 2 帧下一波出怪时读到 1/1，对局继续，第 8 帧击杀最后一只怪并胜利。反例保留旧怪，第 2 帧新波刷出后读到 2/1，并在该帧直接判负。用 1×、4×、后台补算和第 1 帧写入快照后刷新比较完整事件顺序、胜负及最终状态。后台补算用同一时钟入口推进。浏览器另外检查两张贴图、队伍光晕、攻击动画和鼠标选中。保持战斗输入相同，更换模型及播放动画后重跑，比较射程、碰撞及最终状态。

**首版原型历史结果**。采用当时的下一帧检查规则，桌面 Chrome 中，1×、4×、模拟后台补算以及第 2 帧提交 IndexedDB 快照后刷新续局，其事件顺序与最终快照完全一致，均在第 8 帧胜利。另用 Chrome 冻结并恢复页面，结果相同。取消第 3 帧攻击时，第 3 帧按 2/1 判负。实际加载四糸乃后，两张贴图和队伍光晕显示，待机与攻击动画切换正常，鼠标可选中塔和敌人，超出射程的攻击被拒绝。播放动画和切换模型后，同组输入的碰撞、战斗事件与快照一致。首个桌面里程碑采用 `war3-model` 直接加载 MDX/BLP1，移动设备和无尽高负载留待对应阶段实测。原型运行说明见 [首个战斗验证场景](../prototypes/first-battle/README.md)。

### 首个里程碑复审稿

以下是针对 R1–R4 的 P3 修订，已纳入下文 G5 架构基线 v1.0。首个里程碑为桌面短主线与无尽。

#### R1 局内命令与提交

对局状态由玩法层统一持有。页面提交带对局 ID、命令 ID 和参数的意图。玩法层为本局接受的命令分配单调序号，按目标帧和序号处理。新意图归入下一个尚未处理的逻辑帧。同帧经济命令先于攻击阶段提交，因此即使攻击指令先发送，攻击仍读取本帧升级后属性。重试沿用原命令 ID，返还原执行结果；排队中的重复命令合并。加载模型、动画和选中状态由表现层单独处理。

| 命令 | 前置校验 | 同一帧内的提交 | 成功与拒绝例 |
| --- | --- | --- | --- |
| 建造 | 主线或无尽运行中，位置合法且空闲，持有指定卡片，金币足够 | 消耗卡片和金币，写入占位与新塔实例 | 空位建塔后金币减少且塔存在；位置被占时金币和卡片原样保留。 |
| 升级 | 塔仍存在、可升级、金币足够 | 扣费并更新等级和派生属性；当前冷却到期帧继续有效，下一次攻击使用新间隔 | 升级后攻击力立即用新值，现有冷却继续；金币不足时塔等级和冷却保持原值。 |
| 抽卡 | 卡池可用、金币足够、存在可接收位置 | 扣费、推进随机状态并登记卡片实例 | 同一命令重复发送只获得一张牌；容量不足时金币、卡片和随机状态保持原值。 |
| 购买 | 商品及库存有效，金币足够，存在可接收位置 | 扣费、扣库存并登记物品实例及归属 | 两条指令争抢最后一件时，先到者获得商品，后到者收到售罄且无扣费。 |
| 合成 | 配方匹配、材料实例互异且归属本局、费用足够，计算消耗后有产物位置 | 消耗材料和金币，登记产物实例及归属 | 同帧先购买可供后续合成；两条合成指令共用材料时，后到者收到材料无效且无扣费。 |

校验使用前一条命令提交后的状态。失败返回原因，业务状态与随机数保持原值。成功、拒绝及其命令序号一同进入帧末快照，成功操作触发立即保存请求。提交前的已持久化快照包含已排队的命令，恢复后执行一次；提交后的快照包含结果，重试只读取结果。仅在事务完成后显示已保存。

#### R2 主线与无尽的生命周期

对局模块持有阶段、波次及当前和最后完成的波次编号。波次配置提供出怪计划，战斗模块报告本帧结算结果。阶段依次为新局初始化、主线运行、主线胜利等待、无尽运行、失败结算。主线也可直接进入失败结算。重开使用新对局 ID 初始化。

| 转移 | 触发和原子更新 |
| --- | --- |
| 新局 → 主线 | 创建对局 ID、初始状态、种子和首波事件，请求保存。 |
| 主线 → 胜利等待 | 最后一波完成全部出怪且清场，本帧容怪检查通过。记录主线胜利，暂停对局时间并保存。 |
| 胜利等待 → 无尽 | 玩家操作在阶段边界生效一次，沿用同一对局 ID。初始化无尽第 1 波，最后完成的无尽波次从 0 开始，登记首批事件并保存。重复进入请求返回当前阶段。 |
| 运行 → 失败结算 | 容怪检查失败时优先结算。记录最后已完成的波次，终止推进，取消后续战斗事件和待执行命令，保存终态。 |
| 失败结算 → 新局 | 分配新对局 ID，初始化全套状态，按存档换局规则提交。 |

进入无尽时继承塔实例、位置、等级、技能和剩余冷却、装备实例及归属、背包、卡片、资源与随机状态。清理主线波次专属的剩余事件及未执行的主线命令。继承单位、技能或装备的持续效果保留其到期事件与剩余时长。首版无尽初始化独立商店库存，库存和价格规则由内容配置决定。每波完成条件为本波已全部出怪且本波敌人清零；更新最后连续完成的波次。内容配置决定下一波首批出怪时刻，允许前波敌人仍留在圈内。无尽按波次编号和明确配置的成长公式生成新波，每次只排下一波。单位 ID 和事件序号在同一对局内持续递增。示例中无尽第 6 波首批出怪时失败，记录第 5 波，恢复失败快照后保持该结算。

#### R3 帧顺序、容怪检查与时钟

帧顺序为局内命令提交、移动及碰撞、推进冷却、出怪、新一波首批出怪后检查容怪、执行攻击与技能并结算伤害和死亡、推进波次或终局、捕获帧末快照。攻击与技能阶段先按命令序号执行玩家指令，再按单位 ID 执行自动攻击。冷却到期的单位可在该帧攻击；每次攻击前重新确认目标仍存活。位置条件相同的候选按单位 ID 打破平局。事件按目标帧、阶段、序号排序。事件若要写入已处理的阶段，最早安排到下一帧。技能的即时伤害在攻击与技能阶段内按触发顺序执行。

**判负仅发生在下一波首批出怪的边界。** 将该时点同时刷出的单位统一加入战场，再检查一次圈内存活敌人的容怪点数。此处判负则停止本帧的后续战斗，保留此前已经完成的波次数。当前原型用一维路线上的闭区间表示圈内，边界点计入。

逻辑帧使用固定步长，步长随当前规则版本固定。1×、4×及后台补算使用同一推进函数与帧顺序。暂停或改速前，先把截至操作时刻的现实时间按旧速度入账，保留不足一帧的余量；暂停期间时钟停止。改速后新增时间采用新速度。活页面恢复后按挂起前的速度补算，长补算可分批推进并保留剩余时间；期间到达的玩法输入排在补算结束后的首个可执行帧。到主线胜利等待或失败时停止并清除超出停点的时间。关闭或系统回收后，从已保存逻辑帧、速度、暂停状态和时钟余量建立新锚点，离开期间不补算。如果快照记录了尚未处理完的已入账逻辑帧，启动时先处理这批帧，再处理新页面收到的指令。

普通启动先等待 IndexedDB 读取完成，再允许操作或写入新局。帧末快照完整复制，通过单事务替换 `current`。保存协调器同一时刻只提交一份，并仅保留最新一份尚未开始的快照。事务完成才更新最近成功标记。事务拒绝或中止时保留最近成功的记录，释放当前写入并继续处理待写快照。切换阶段和重开都请求保存。重开时撤销还未开始的旧局保存，等待已开始的旧事务完成，再提交新局；旧事务可以完成磁盘提交，旧回调不更新新局的界面状态。新局事务完成前刷新时，读取最近实际成功的旧快照。启动、保存失败和不兼容均提供明确状态反馈。
