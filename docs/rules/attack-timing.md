# 攻速与攻击计时

本页为 `attack-timing-v1`，只确定共享攻击速度、攻击冷却及前后摇的接口和计时。原图字段/指令、外部一手资料、Q24 下的 Web 选择分开列出；没有运行 Warcraft 客户端，也没有以另一引擎的代码证明本图客户端行为。机器表见 [attack-timing.json](attack-timing.json)。Q35 已确定 A022 的加成输入为 +5。此前把 A163 的图鉴行错配给 A180 的记录已更正：集中火力减0.2与其脚本一致，无影拳设0.3属于图鉴缺项的原图补充。

## 1. 原图输入与一手接口证据

[war3mapMisc.txt](../../reference/map-6.25/war3mapMisc.txt#L7) 明示 `AgiAttackSpeedBonus=0.002`，L26 为 `FrostAttackSpeedDecrease=0.6`，L41 为 `IllusionsGetAttackSpeedBonus=1`。该覆盖文件没有总攻速上/下限字段。冰冻的 0.6 是已确认的配置值，不表示所有减速技能一律减少 60%；具体能力仍负责登记自己的有效输入和生命周期。

[暴雪 Hero Basics](https://classic.battle.net/war3/basics/heroes.shtml) 给出的攻击冷却公式将敏捷、物品、能力的攻速增加量相加，然后用基础间隔除以 `1+加成`。该图的敏捷系数用明确的 0.002 覆盖普通游戏的 0.02。官方页面未证明本图总攻速界限、当前攻击重计时或后摇截断的细节。

[YDWE 扩展原作者的固定版本 UnitState.cpp](https://github.com/actboy168/YDWE/blob/a69c315ebf2886ec54d66200707ab6e38bd3484d/Development/Plugin/Warcraft3/yd_jass_api/UnitState.cpp#L31) 提供以下独立字段和直接读写接口。该源码用于解释 JAPI 状态含义，不是本图所装扩展二进制版本的证明；本图 w3i/editor 版本也不能证明运行客户端版本。

## 4. T01：汇总原始系数，最后限幅

以下为明确的 **Web 选择**，不是宣称原版实测结果：

```text
R = 1 + 0.002 * A + Σ(当前有效的攻速贡献) + J
K = min(5, max(0.2, R))
```

A 是原生英雄当前敏捷，包含已经生效的敏捷增益；无英雄敏捷的单位此项为0。这里不采用地图自定义、用于 Boss 等判定的 `UnitIsHero`。每个能力/装备模块先解决它自己的有效性、互斥、刷新和撤销，再向共享系统提交贡献；不能从所有物品/能力字段无条件求和。`+40%` 输入 0.4，`-60%` 输入 -0.6；加成之间不连乘。幻象配置保留，但本页不把它扩成“复制原塔全部 Buff 实例”。

J 是脚本直接写入所形成的差额：`SetUnitState(u,81,v)` 令 `J += v - 当前R`，getter 返回完整 R。之后敏捷/有效 Buff 变化继续保留 J。这是对原生后续重算仍未知之处的 Web 定义。`Set37(v)` 则直接替换基础 C，按原脚本顺序执行，不套一个自作主张的全量减间隔累加器。

**上下界 0.2 与 5 是本 Web 基准明确选定的常数**（总速率为基础的20%至500%，相对于基础即-80%至+400%）。一手公式和本图字段没有证明这两个端点；选有限正下界可使受减速的攻击仍推进，有限上界使常规加成饱和，而直接改变 C 仍能改变最终频率。该选值不以 Warsmash 的 -90%/+400% 实现或论坛说法冒充原版事实。限幅包含直接 JAPI 加成在内的总 R；JAPI 在实际引擎能否绕过限制仍没有匹配版本证据。

只在调度时使用 K，**不把夹紧结果写回 R**。例如 R=5.6，再加5得10.6，K始终5；减回5后 R仍5.6、K仍5。否则把10.6存成5再减5会错误清空其他攻速。R仍可用于原地图自己的计算；本页不把原公式中的 R、负值或零值偷偷改成 K。

## 5. T02：冷却与前后摇的时间轴

对某次被选中的武器，读取独立的 C、P、B。持续攻击同一有效目标、没有中断且速率恒定时，Web 采用：

```text
冷却门槛时间 = Ceff / K
前摇完成时间 = P / K
完整后摇时长 = B / K（从前摇完成时开始）
下一次攻击开始 = max(Ceff, P) / K
Ceff = max(C, 0.000001秒)
```

冷却在攻击开始时启动，与前摇并行；不是命中后才开始计时。前摇完成只发出一次“该次攻击已提交”的通知，命中/弹道/伤害另走对应系统，本页不定义它们。后摇是可中断的恢复动画：它未结束时，下一次已就绪的连续攻击可以截断后摇；后摇结束也不会清空尚未到期的冷却。P大于C时，先等本次前摇提交再允许下一次开始，不允许同一武器并行堆积多次前摇。它是本页明确选定的 Web 行为，未声称匹配原生边界。

Ceff 的1微秒仅是 Web 对直接脚本写入非正间隔的防止零时循环保护；getter仍返回原始C，不冒充 Warcraft 的0.1/0.02秒硬限制。有效对象的 P、B 必须有已解析的非负数值；缺省未解析不能补0。显式 P=0/B=0 可作为零长度阶段，提交仍只能一次。零时阶段回调按B05进入当前时刻队尾，不能内联递归无限开攻。

例如 E014在K=1时：0开始，0.35提交，0.95下一次开始并截断剩余0.05后摇；不等到1.00。**原图补缺与 Web 时序的组合例：** 将A180原脚本C=0.3传入，G065的P=0.35、K=5，冷却0.06、提交0.07，所以连续攻击间距0.07；这是 Web 时序推导，不能伪称原客户端实际每秒攻击次数。

攻击开始事件只发一次，沿用原图 `chooseAttackedAction`；A022在这个事件中触发时，能影响刚开始且进度为0的当前前摇。不会为了新攻速额外发第二次攻击事件。攻击中断的其他原因、施法/移动命令是否中断，以及命中判定不由本页额外规定。

## 6. T03：进行中变速与存档

沿用 A022 已定的“保存未完成标准化阶段工作量”。每个尚未完成的门槛/阶段独立保存已完成比例：冷却 `pc`、前摇 `pp`、当前后摇 `pb`。旧速率推进到变更战斗时刻后，保留这些比例；新速率改变剩余时间，不从头开始、不补发攻击。只改 K 时，每个未完成阶段的 `新剩余秒=旧剩余秒*Kold/Knew`。

直接改变 C 只影响尚未完成的冷却门槛：保留pc，余时变为 `(1-pc)*Ceff_new/Knew`；不改P或B。若C同时改变，冷却余时也可写成 `旧余时*(Ceff_new/Ceff_old)*(Kold/Knew)`。已就绪的冷却不因加长C重新关闭。后摇只在已经提交后计时；前摇尚未提交时，新K也用于随后开始的后摇。已经提交的攻击与独立弹道不回溯重做。

调度沿用 [B05](web-baseline.md#b05同一时刻的计时事件按入队顺序执行) 的整数微秒与本次入队序号。正余时四舍五入到微秒，若舍入为0则安排下一微秒，防止有正工作量却在当前时刻无限循环；显式零阶段仍可队尾执行。重计时使旧完成条目失效并按新截止时间重新入队。**若K未变化，或对应阶段在该时刻已经完成工作且原完成事件正在同刻等待，不重新排队**；到期与状态修改谁先执行仍由既有B05序号决定。阶段提交用攻击代号/阶段代号保证只发生一次。

存档至少保存规则版本、原始 C/P/B/R 及其贡献/J、当前武器和攻击代号、阶段已完成比例/上次积分时刻、阶段状态、待执行事件截止时刻/序号和失效代号。恢复不再应用一次Buff、不重复扣/加J、不重发攻击事件。4×、暂停和后台补算只改变战斗时间推进，不改变上述比例或排序。
