# 未证实原生细节的 Web 基准

Q24 已授权在查证后仍无充分证据的底层行为上制定明确规则。本页为 `web-baseline-v1`，不是原版实测结果，也不是整个游戏规则的替代品。图鉴明文、已确认的用户裁决和已核脚本优先；有来源但尚未读完的技能、装备、变身和建造逻辑不能用本页默认规则代替。

本轮落实下列五项。每项的数学或顺序例子是实现时的验收依据；当前只校验规格数据，尚未构建游戏运行时。机器表见 [web-baseline.json](web-baseline.json)。原生证据与实测缺口保留在 [原生护甲与经验](native-armor-and-xp.md)，便于以后取得客户端时对比。

## B01：负护甲使用固定 0.94 底数

**证据：** [暴雪公开公式](https://classic.battle.net/war3/basics/armorandweapontypes.shtml) 给出负甲承伤倍率；原图物理事件另除以分段函数 G(a)，在 -10、-20 附近接近该曲线。原图无法证明修改 `DefenseArmor` 是否同时改变负甲指数底数。

**Web 选择：** 非负护甲使用已确认的 `F(a)=1/(1+0.018*a)`；负护甲使用 `F(a)=2-0.94^(-a)`，不把底数改为 0.982。只对按伤害入口规则应受护甲影响的伤害应用 F；伤害类别倍率与魔抗分别处理。保留原图 G(a) 修正的触发条件及执行位置，不能为了“抵消”负甲而删除它。

**验收例：** 护甲 -10 的护甲层承伤倍率为 `1.4613848859051003`；若随后满足原图 G(-10)=1.46 的修正条件，且无其他修改，两层合计倍率约 `1.0009485520`。这个接近 1 的结果不应强行舍为 1。金币怪被 G 分支排除，仍按其对应分支计算。

## B02：经验表逐项向下取整

**证据：** 地图给出了三组经验起点和 A=1.4；[官方经验说明](https://classic.battle.net/war3/basics/heroes.shtml) 和 [原始数据注释](native-armor-and-xp.md) 支持递推形式及累计阈值含义，但未证明小数系数在每一步还是最后一步转换成整数。

**Web 选择：** 每生成一项经验表，就向下取整并将该整数用于下一项；用精确的 7/5 表示 1.4，避免实现语言的浮点误差使整数边界少 1。仅这三张经验表采用此取整规则，不把所有技能伤害、属性和持续时间都取整。

```text
累计升级阈值 T(1)=0，T(2)=20
T(n)=floor(7*T(n-1)/5 + 20*n)       n>=3

普通单位基础击杀经验 N(1)=2
N(n)=floor(7*N(n-1)/5 + 2*n)        n>=2

原生英雄基础击杀经验 H(1)=30
H(n)=floor(7*H(n-1)/5 + 30*n)       n>=2
```

明确列出的表项优先，表尾才递推；当前地图每组只有一个起点。累计经验达到 `>= T(n)` 即达到该级门槛，不能将 T 再逐级累加。普通/原生英雄分类、死亡单位等级、经验范围、分摊及脚本剥离等级依各自规则，不能以主线波号替代 n。

**验收例：** T(2..8) 为 `20,88,203,384,657,1059,1642`；累计经验 1641 不达 8 级，1642 达 8 级。N(1..3) 为 `2,6,14`；H(1..3) 为 `30,102,232`。这些是本基准的确定结果，不声称与原客户端小数处理一致。机器表给出 1–30 级，超过 30 的死亡单位仍按同一递推延伸基础经验表。

## B03：伤害事件读取减免后的值，改写后不重复减免

**证据：** 原图不断读取、改写当前事件值；[YDWE 扩展作者源码](https://github.com/actboy168/YDWE/blob/a69c315ebf2886ec54d66200707ab6e38bd3484d/Development/Plugin/Warcraft3/yd_jass_api/EventDamageData.cpp) 用栈隔离嵌套事件，并把改写值用于伤害提交。它没有完整证明该图实际客户端的护甲位置。

**Web 选择：** 一次伤害先由其入口规则执行适用的原生减免，再进入地图伤害事件。`GetEventDamage` 返回当前事件可变值，`EXSetEventDamage` 替换此值；事件链结束后按改写值提交，不再重复乘护甲或类别倍率。生命下限、死亡通知等提交行为与事件内读写分开处理，不因某个中间值超过目标生命而提前删除单位。

嵌套伤害同步压入独立事件上下文；子事件提交后恢复父事件的来源、目标、类别和当前伤害。脚本普通全局变量仍按原程序处理，不把它们全部自动快照恢复。主事件、前后置装备分派的短路、早退和读入快照位置沿用现有规则。原脚本明确写零后继续的分支不能新增统一早退。

**验收例：** 已确定应经过正护甲层的原始伤害 280、护甲 100、其余倍率 1，事件入口为 100；事件将它改为 150，最终提交 150，而不是再乘 1/2.8。父事件当前值 100 时制造子伤害，子事件改为 7 并提交，返回后父事件仍读 100。

此规则只确定提交时序；它不替代各 damage type 是否受护甲/魔抗影响的分类调查，也不裁决 A026 提示与脚本的差异。

## B04：组枚举采用稳定的单位创建顺序

**证据：** 自动施法用 `FirstOfGroup` 获取首个符合者，原图没有指定最近、最前或最低血量，原生枚举顺序无法确认。

**Web 选择：** 已按脚本条件取得的候选组按单位创建序号升序枚举。序号在本局单调增加，移除单位不复用，存档恢复保留。空间查询结构、渲染批次或模型加载完成顺序不得影响它。仍按原来的 `hasMon/hasHero/hasNor` 谓词逐个过滤；重新枚举就是重新读取候选集合。

**验收例：** 满足同一个查询的创建序号 12、4、9 中，若 4 不满足 `hasHero`、9 与 12 满足，应取 9；普通 hasMon 若三者均满足则取 4。距离较近不会自动覆盖这个顺序。该选择可能与原生隐藏枚举顺序不同，是明确的 Web 差异。

## B05：同一时刻的计时事件按入队顺序执行

**证据：** 原图使用即时调用、周期计时器及 timeout=0 单次计时器；没有可用运行证据证明同一时刻的底层排序。暂停、4×与后台补算必须使用同一套战斗时间语义。

**Web 选择：** 战斗时间使用整数微秒；脚本秒数乘 1,000,000 后取最近整数，正中间时向上取整。计时事件按 `(到期战斗时间, 本次入队序号)` 排序；每次入队取得新的单调序号。零秒单次回调进入当前战斗时刻队尾，在当前调用栈返回后执行，不内联、不强制延迟一个渲染帧。周期事件从本次计划到期时间加周期计算下一次到期，不能从渲染帧或墙上时间重新起算。

取消事件使其对应待执行条目失效；同刻较早执行的停止事件能取消同刻尚未执行的刷怪事件。回调创建的零秒事件排在已经入队的同刻事件之后。倍速只改变墙上时间向战斗时间的推进量，暂停不推进；续局和后台补算恢复同一个队列与序号。禁止将技能/波次按浏览器计时器自然调度顺序分散执行。

**验收例：** 同刻已有 A(序号10)、B(11)，A 执行时又登记零秒 C(12)，执行顺序为 A、B、C。若 A 取消 B，则为 A、C。计划在 1、2、3 秒触发的周期事件，即使一次补算到 3.5 秒，也仍依次处理 1、2、3 秒，而不是只执行一次。原波次同刻末批与停止的数量范围应在实现原脚本登记顺序后据此收敛，不能先任取范围上限或下限。
