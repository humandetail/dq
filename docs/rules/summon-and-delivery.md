# 卡片召唤、失败回退与满背包交付

本批闭合了原图的卡片人口预检、召唤相关脚本是否另扣目标塔价格，以及 15 处物品交付调用的失败分支。**脚本没有在卡片使用时另扣目标塔金币／木材；人口预检实际读取卡片当前生命值。** 第二轮补齐施工时长、完成／取消和普通商店满包准入的可实施 Web 规则。原生 `AIbl` 的内部收费、缺省时长和取消退款仍无匹配客户端实测；下文把对象事实、脚本事实和 Q24 选择分别记录。

机器数据见 [summon-and-delivery.json](summon-and-delivery.json)。本页只补召唤与交付边界；不改图鉴、对象快照、现有经济规则，也不把物品对象标价、单位对象建造价和回收基数相加。

## 召唤命令的真实预检

`Skill_Trig_Init` 安装 `Trig_Order_Build_Event`，对 Player(0..3) 监听 `EVENT_PLAYER_UNIT_ISSUED_POINT_ORDER`，调用 `OrderBuildEvent`。[Lua L125254–125298](../../reference/map-6.25/main.readable.lua#L125254)、[L125443–125464](../../reference/map-6.25/main.readable.lua#L125443)

以下控制流已核 `main/f291/f19`，不依赖反编译缩进：[字节码 L172980–173118](../../reference/map-6.25/main.disasm#L172980)，阅读位置 [Lua L119243–119338](../../reference/map-6.25/main.readable.lua#L119243)。

1. 只处理 `IsWorker(orderedUnit) OR IsBOX(orderedUnit)`，且 `852008 <= orderId <= 852013` 的点命令。物品槽为 `orderId−852008`，即 0–5。代码没有先确认它属于某个召唤卡 ID；不能把原判断伪写为“仅 I501 等卡片触发”。
2. 取该槽物品；先调用目标点的 `IsTerrainPathable(x,y,PATHING_TYPE_BUILDABILITY)`。为真时提示不能建造，发 `stop`，再发移动到施令单位当前位置的 `move`，跳过人口分支。
3. 地表检查通过后计算 `GetWidgetLife(item) + GetPlayerState(owner, PLAYER_STATE_RESOURCE_FOOD_USED)`，与 `PLAYER_STATE_FOOD_CAP_CEILING` 比较。**严格大于**才提示人口已满，并发同样的 `stop → move`；等于上限不被此脚本拦截。比较指令是 [L173093](../../reference/map-6.25/main.disasm#L173093) 的 `lt r5,r4`。
4. 上述拒绝路径没有 `RemoveItem`、`SetItemCharges`、`SetPlayerState`、资源返还或重新创建卡片，也没有检查 `stop/move` 的返回值。它们只是尝试阻止原生命令，不能据此证明原客户端任何情况下都未消耗卡片。

`GetWidgetLife(item)` 是实例**当前**生命，并不是 `HP` 最大值，也不是直接调用目标塔的 `GetUnitFoodUsed`。未受损卡片的数据与 `fused` 全部一致；一旦实例生命不同，不能悄悄把这条原脚本改写为固定对象 HP。当前人口上限的 30/50/70/90/100 仍依[经济规则](economy-and-progression.md#开局与人口)。

这条预检只查目标点的地表；完整建筑占用、路径贴图与合法放置由[战场规则](battlefield.md)继续承担，本页不以一次地表查询代替全部放置许可。

## 施工时长、种族和取消的证据边界

87 个召唤能力的完整 SLK 行均只有 `alias、code、levels、Rng1、targs1…4、UnitID1` 九个字段；均为 `code=AIbl、levels=1、Rng1=100、targs1…4="_"`。每个能力的四个种族目标相同，全部 87 个目标的 `bldtm=1`。机器表 `constructionEvidence.abilities` 保留全部能力行与字段行号，`targets` 保留目标建造时间和种族来源，不能只看一个样例外推全表。样例：[I501 L22964–22972](../../reference/map-6.25/units_abilitydata.json#L22964)、[H001.bldtm L26138](../../reference/map-6.25/units_unitbalance.json#L26138)。

自定义行没有 `Dur1/HeroDur1`，`.w3a` 也没有补写；基础 [AIbl L3006–3015](../../reference/map-6.25/units_abilitydata.json#L3006) 则明确 `Dur1=30`。这不能证明自定义缺项继承 30，也不能证明引擎改用单位的 1 秒。ScrewTheTrees 的[能力研究原文](https://docs.google.com/document/d/1z17FTnhyfVL87tJgLmwWks3Low6TuQ0tjfKHXBELWpo/edit)之 Build Tiny X 条目（[2023-11-14 文本存档](https://github.com/Cokemonkey11/wc3-ability-doc/blob/main/sources/screwthetrees-wc3-editor-ability-insight-document/2023-11-14.md)，标注测试版本 1.28.5.7680）说明普通持续时间控制施工，并可产生完成事件。这是作者的版本限定观察，不是本图缺字段加载规则的证明；本轮仅链接，未复制该文档。

目标的 `race` 分布为 creeps 28、human 27、undead 11、nightelf 11、orc 10，说明不能将 87 个目标全部套进同一普通工人的种族施工规则。例如 [H001.race L13530](../../reference/map-6.25/units_unitdata.json#L13530) 是 creeps，[H003.race L13563](../../reference/map-6.25/units_unitdata.json#L13563) 是 human；目标种族也不等于当前玩家种族。暴雪说明 tiny-building 存在施工过程，并明确 Tiny Great Hall 可以[不依靠 Peon 建造](https://classic.battle.net/war3/orc/voodoolounge.shtml)。它没有说明本图这些自定义目标是否要求持续施工、如何解析缺失时长；S03 为这部分提供确定结果，不添加五套猜测的工人流程。

完成处理本身已经闭合：`CONSTRUCT_FINISH/UPGRADE_FINISH → anyBuildComplete → anyBuildCompleteHandler`；后者先登记 `Tower_ALL` 和 user data，再设置能力、停止命令、魔法等，符合 **原生英雄类型或 n208** 时才抽 `GetRandomInt(1,13)` 的资格。这里的谓词是 `IsUnitType(..., UNIT_TYPE_HERO)`，不是另一个自定义 `UnitIsHero`。参见[字节码 L167771–167956](../../reference/map-6.25/main.disasm#L167771)。因此施工开始时不能提前运行完成处理或预抽资格。

取消方面，脚本中 `CONSTRUCT_START/CANCEL` 的登记只在通用 `MeleeInitVictoryDefeat` 库代码处找到，未发现本图自定义的取消返卡／目标价退款处理。库内取消回调仅把 `GetCancelledStructure()` 交给 `MeleeCheckLostUnit`，不是返卡函数：[Lua L27861–27868](../../reference/map-6.25/main.readable.lua#L27861)、[登记 L28361–28393](../../reference/map-6.25/main.readable.lua#L28361)。[暴雪普通建造退款页](https://classic.battle.net/war3/basics/buildings.shtml)讨论资源返还，而本图的 `ConstructionRefundRate=1.0`、`UpgradeRefundRate=1.0` 也只是比率（[Misc L12](../../reference/map-6.25/war3mapMisc.txt#L12)、[L58](../../reference/map-6.25/war3mapMisc.txt#L58)）。它们没有证明 AIbl 取消会返还卡片、返还目标对象价或使用何种计价基数。S04 明确退款对象，不能将普通资源比例直接乘卡片标价。

普通商店的购买准入与已经创建物品后的交付是两个边界。地图的 14 项叠充能白名单是 `i127、i128、i001、i002、i003、i005、i235、i258、i259、i260、i329、y006、y008、y010`，已核[字节码 L142997–143040](../../reference/map-6.25/main.disasm#L142997)。它们不是“所有 Charged 类物品”。`HasItem` 按槽 0–5 找第一个相同 ID 且不是当前 `GetManipulatedItem()` 的实例；合成尝试在叠充能之前，叠充能成功将两者充能相加、删除新拾取实例并返回：[Lua L96431–96459](../../reference/map-6.25/main.readable.lua#L96431)、[字节码 main/f285/f8 L144417–144461](../../reference/map-6.25/main.disasm#L144417)、[叠充能 L145278–145306](../../reference/map-6.25/main.disasm#L145278)。

[暴雪物品说明](https://classic.battle.net/war3/basics/heroitems.shtml)支持六槽、单件占一槽，以及 power-up 拾取即用的分类；并没有规定本图自定义商店遇满包、同 ID 充能、合成材料时的购买准入。机器表保留白名单物品的 `class/uses/powerup/stockMax/stockRegen` 等原始值和缺项；例如 [i001 L6459](../../reference/map-6.25/units_itemdata.json#L6459) 的 `uses=1` 不等于原生支持满包自动叠充能。D02 明确采用“先取得一个真实空槽，再让原拾取脚本处理”的 Web 行为。

## Q24 下采用的 Web 规则

以下是本批选择 `summon-and-delivery-v2`，**不是原版实测结果**。既定金币、人口和资格门槛继续保留，地图等级适配按既有决策执行。

**S01：使用已经取得的 AIbl 卡片，不另收目标塔金币或木材。** 本次使用的额外资源成本明确为 0；这是用来替代未证实的 AIbl 原生收费行为，绝不是将缺失的对象价读成 0。之前的购卡、抽卡、兑换或奖励条件已经各自结算，召唤失败不撤销这些已完成交易。普通工人直接建造和升级仍走各自的对象成本，本条不适用它们。

**S02：创建与人口、1 次充能一起提交。** 选位置和预览不扣人口或充能。在实际放置提交时，复查施令单位和卡片仍有效且归属正确、至少 1 次充能、已知前置条件和完整放置条件；执行原脚本地表优先与当前卡片 HP 人口预检。另以 `已用人口 + 目标 fused <= FOOD_CAP_CEILING` 作为 Web 对未知原生准入检查的明确替代，防止卡片受损时按其较低当前 HP 绕过真实人口。后一个 `fused` 检查不是 Lua 已证事实。

所有检查通过后，在同一次战斗时间操作内创建**一只**对应目标、将其 `fused` 计入已用人口、卡片 `charges−=1`。只有剩余充能为 0 的易消耗物品才删除；不能无条件删整张多充能物品。建造完成回调执行既有登记逻辑，不再重复增加人口。若失败或取消发生在提交前，以上三项均不提交；金币／木材也没有本次额外支出。创建成功之后的单位死亡或完成后的回收属于后续生命周期，不当作召唤失败退卡；尚在施工的主动取消按 S04 处理。

同刻多次召唤遵循 B05 已选队列顺序，各次提交读取最新人口；先完成的创建会占用后续命令可用人口。预览不是占位或人口预留。若数据加载缺少必要的人口、充能或许可字段，应报告该规则缺项；本批 149 行已经有明确人口与初始充能，不需要缺值默认零。

**S03：卡片施工使用目标 `bldtm`，本批全部为 1 战斗秒。** S02 提交即进入施工态、占地并计人口；在 `commitTime + 1 秒` 登记一次完成事件，遵循 [B05](web-baseline.md)。此处主动采用已知目标字段作为 Web 时长，不宣称它就是缺失 `AIbl.Dur1` 的原生解析结果。工人／能量圈提交后可以离开，不要求持续施法、驻留或额外工人加速，也不按目标 race 切换施工流程。施工态不能攻击、主动施法、使用／接收物品、升级或回收；可执行 S04 的取消。施工状态不额外改变单位原有可受伤／无敌等属性。

到时仅在施工实例仍存在且状态为 `constructing` 时转为 `ready`，同步调用原完成处理一次，之后才能参与塔的战斗与操作；原处理中的资格抽取和任务变化仍按原谓词发生。不在预览／提交时预抽资格，不重复计人口。施工中死亡或移除使完成事件失效，并释放该实例的人口一次，不返卡。施工时间使用战斗时钟，受暂停与倍速控制；存档保存剩余战斗时间、状态和完成事件身份，续局不能重建一只或多触发一次完成。

**S04：已提交、尚未完成的主动取消，返还本次 1 次卡片充能。** 只允许所属玩家对 `constructing` 实例执行一次；取消与状态检查原子完成：置 `cancelled`、移除施工实例／占地、释放它已记入的人口、使完成事件失效，再返还一次消耗。金币／木材返还均为 0，因为 S01 没有在此处收取它们；购卡、抽卡或兑换的既有成本不退，不能按目标塔标价或回收比例发钱。

提交时保存返还凭据：原卡实例 ID、物品类型、当前 HP 及其余实例属性、施令者、所属玩家、施工坐标和本次消耗 1 次。取消时，若原卡实例仍在同一有效施令者的背包且仍属原玩家，给该实例增加 1 次充能；这是撤回本次扣减，不是任意同 ID 物品自动叠加。否则只创建一个同类型、同所存属性但充能为 1 的返还实例，**创建坐标为施工位置**；原施令者仍存活、归属正确且能携带时按 D01 尝试交付，满包或施令者无效则留在该位置。退款凭据只能兑现一次，随存档持久化；不能把已删除的旧实例重新激活后再同时创建新实例。此规则不会返还整张多充能卡，不会抹去其他已成功施工的扣减。

取消不执行塔死亡击杀／回收奖励，不运行建造完成或资格抽取。完成以后不再提供施工取消，按既有回收规则处理。伤害导致的死亡不是主动取消，沿用 S02/S03 不返卡。同一时间的完成与取消服从 B05：先执行取消则后续完成失效；先执行完成则取消因已 `ready` 被拒绝。通常完成事件在提交时已入队，随后才入队的同刻取消应当排在它后面，不能为了退卡人为提高取消优先级。

**D01：脚本先创建、再加包，满包则保留地上实例。** 本条替代这些明确 `CreateItem → UnitAddItem` 调用及同义助手的底层交付；普通原生商店的交易准入另用 D02。先按脚本坐标创建一次；add 时有空槽则使用 0–5 中编号最小的空槽，入槽后同步执行原 `Item_Get`，保留其移出、删除、合成、叠充能及成品再次触发拾取的语义。脚本明确删除的对象不能被交付层复活。

add 时没有空槽则返回失败，物品留在**原创建坐标**，保留既定 ID、充能与实例身份；不执行这次未发生的拾取事件，不先在地上自动叠充能／合成，也不挤掉旧物品。此前已确定的抽卡结果、材料消耗、活动积分和一次性标志不因满包重置；只需要之后腾槽拾取同一物品。续局保存该地上物品与已完成的前序状态，不能登录后再生成一份。此规则不覆盖任何明确的 `RemoveItem` 或 `UnitRemoveItem` 分支。

**D02：普通实体商品须有空槽才能购买，可叠充能也一样。** 适用于通常经原生商店出售、随后作为实体物品入包的商品。先检查原有购买资格、已确定的价格／余额、库存和接收者有效性，再检查当刻是否至少有一个空槽；未通过则整笔拒绝，不扣币、不减库存、不创建商品，也不触发销售／拾取回调。不能把缺失价格当 0；是否可售与价格取已闭合的对应商品规则。

即使背包已有同 ID 白名单物品，或买入后可能合成腾槽，满六槽仍拒绝。通过时以同一个队列操作提交费用、库存和实体入槽，再同步执行原 `Item_Get`：先原有资格／合成等分支，再原有白名单叠充能。若这些脚本随后明确丢出、删除物品，则保留其结果，不撤销已完成购买。不存在“先在地上叠充能，再决定是否买入”的路径，也不为普通满包购买创建落地商品。D01 的脚本奖励／合成已经先创建物品，两者不能混为一类失败。

对**明确 `powerup=1`** 的拾取即用商品，D02 仅免除空槽检查，既定有效对象、资格、价格和库存仍需通过，不挤走原有物品；其已定义效果照旧。缺失 `powerup` 保留为空值，Web 明确只给显式 1 这个例外，不把字段缺省值伪写为原生 0。菜单兑换／翻页等虚拟操作继续用各自脚本与已选 Web 适配，不套用实体购买来额外限制已授权菜单；本条也没有重排抽卡道具最后一次充能与奖励回调。
