## 2. 主线开局、计时与数量

### 2.1 完整开波链

**事实。** 完成难度选择调用 `ChooseLvHandler`，初始化容怪面板后 `timeToStart` 安排 5 秒的单次触发器调用 `game_start`。`game_start` 调用 `MonsterShow_showDialog`，首波倒计时是 `time_of_space[1]=32` 秒。因此首怪是 **难度确认后的 37 秒**，不是图鉴 `主线波次!J5=0` 所容易被误解的“立刻出怪”。J 列是 `time_of_delay_show` 数组，不是完整倒计时。证据 L:139863–139872、139969–140029、126200–126313、126716–126780。

一波倒计时结束进入 `MonsterShow_time_end`：

1. 销毁该倒计时和 UI。
2. 先检查上一阶段仍在场的怪物点数，处理超限玩家。
3. 主线设置 `cur_monLv=next_monLv`，随机抽本波 Boss 光环编号 1–4；第 53 波同时启动最终 Boss 的独立 180 秒倒计时。
4. 依次调用 `delayToStopMon()`、`next_monster_time()`、`Trig_monsterShow()`。因此停止事件与下波安排在本波首次出怪之前登记。
5. `Trig_monsterShow` 登记周期出怪触发器，处理本波阶段事件，再立即调用 `Trig_monsterShow_Act` 出第一批；每个活动口一只。

证据 L:127614–127861、128095–128437、129706–129797；周期分支已核对 `B:main/f294/f17`，批次玩家列表已核对 `B:main/f294/f16`。

### 2.2 四个时间数组与可计算时间线

四数组均有 54 项，直接初始化在 L:126200–126639，完整逐波表见 [waves-data.json](waves-data.json)。

- `time_of_show[n]=40`：1–54 波都在开波后 40 秒调用 `StopMon`，关闭并销毁 `_mon_rate_trig`。**停止刷新不等于清掉存活怪物。** 证据 L:129774–129810。
- `time_of_space[n]`：本波 UI 倒计时。5、10、…、50 为 36 秒；6、11、…、51 为 10 秒；其余 32 秒。
- `time_of_delay_show[n]`：从上一波开波起，延后多久创建本波倒计时。第 1 波为 0；6、11、…、51 为 72；其余 18。
- `time_of_show_rate[n]`：周期刷怪间隔，见图鉴 H 列及机器表；不是完整波长。

**推导。** 以 `game_start()` 被调用为 t=0：

```
t[1] = 32
t[n] = t[n-1] + time_of_delay_show[n] + time_of_space[n]   (2 <= n <= 54)
t[55] = t[53] + 180
```

|事件|相对 game_start 秒数|换算|
|---|---:|---|
|第 1 波首批|32|0:32|
|第 5 波首批|236|3:56|
|第 6 波首批|318|5:18|
|第 50 波首批|2810|46:50|
|第 53 波首批并启动肉山倒计时|2992|49:52|
|第 54 波首批|3042|50:42|
|第 54 波福利开始 / 结算|3092 / 3112|51:32 / 51:52|
|肉山首批|3172|52:52|
|肉山超时上限（若未提前全杀）|3652|60:52|

这些时间不含玩家选难度的等待，且相对难度确认还需统一加 5 秒。它们是模拟时间，不是 Web 前后台墙钟策略。

最终 Boss 倒计时 180 的原计算是 `time_of_show[54](40)+time_of_delay_show[54](18)+time_of_space[54](32)+money_dur_time(20)+money_after_time(10)+60`，在 **第 53 波** 开始时登记。不是第 54 波结束再等 180 秒。证据 L:126685–126710、127844–127854、126814–126858。

### 2.3 刷新批次数与同秒边界

**事实。** 首批立即生成，后续每 Δ 秒生成一批，40 秒停止。主线批次无“尚未清怪则等待”的门槛。

**推导。** 若 40/Δ 非整数，批次数为 `ceil(40/Δ)`；若为整数 k，则为 k 或 k+1，取决于 40 秒停止回调与该周期回调的顺序。每口数量等于批次数；活动口数只乘总量。

|0.9|45|无|
|1.1|37|无|
|1.3|31|无|

### 2.4 本波阶段事件

`Trig_monsterShow` 在立即首批之前执行：第 11/21/31/41 波传入人口目标值 `30+20*(n-1)/10`，即 50/70/90/110；`Add_Player_Food` 内先限制至 `FOOD_MAX=100`，再设置人口上限，最终依次 **50/70/90/100**，与图鉴一致。证据 L:128221–128261、137069、140089–140124。第11波开挑战店，第54波清理挑战店；个人模式第20波开资格店，团队第25波；第21波开神秘店；26/31/36/41/46/51/52/53/54 刷新。证据 L:128221–128405。神秘店最终关闭时间见商店规则。

## 3. 容怪与失败

### 3.1 容怪不是生命值，也不是每只固定占一格

`Multiboard_CheckNum_Mode_1` 遍历玩家对应 `Mon_Mode1_0…3`，对非 nil 单位累加 `floor(GetUnitPointValue(unit))`，以 `capacity - sum < 0` 判超限。因此 **等于上限仍可继续**。团队对 `mon_arr` 做同样点数累加。证据 L:36178–36336。

|分支|主线容量|无尽容量|证据|
|---|---:|---:|---|
|个人，只有 1 名活动玩家|100|30|L:35969–35986、36339–36351|
|个人，多名活动玩家|每人70|每人30|同上|
|团队|40+30×活动玩家数|20×第22波锁定玩家数|L:36039–36059、36158–36164、36343–36349|

上表为基础容量。无尽中 `SHOPITEM08 && SHOPITEM01` 还可增加 10 容量。个人对各自检查，团队找到一名符合条件者就增加一次并 break。**Q18 已确认直接开放原平台权益并保留效果，因此单人个人模式 Web 的主线容量为 100、无尽容量为 40（30+10）**；这 10 点只在 `Game_Mode==1` 的无尽阶段增加，不能加到主线。证据 L:36210–36223、36283–36302。

对象点数已从 `Units/UnitData.slk` 的 `points` 列提取，见 [units_unitdata.json](../../reference/map-6.25/units_unitdata.json)，以 `unitID` 定位：

|对象|每只占格|
|---|---:|
|主线 m001–m054、肉山 mBOS|1|
|福利 m998/m999|1|
|无尽普通 mw01–mw04|2|
|无尽 Boss mw11–mw16|5|
|无尽 Boss mw17|10|
|深渊 ma01–ma06、ma99|5|

主线/无尽涉及对象没有 `war3map.w3u` 的二次字段覆盖；源码也未找到运行时修改 point value 的调用。福利单位同样登记到 `mon_arr` / 个人数组并各占1格。**无尽普通一波生成7–8只，实际是新增14–16格**；不能把数组 `length` 当点数。深渊的5是对象字段，不表示深渊另有主线式容怪失败检查。

### 3.2 实际检查时点与“宽限”

**事实。** 面板初始化后每 2 秒调用 `Multiboard_CheckNum_Mode_1` 刷新颜色/数字，它只返回超限玩家数组，并不直接结算。实际把返回玩家传给 `OnePlayerFailed` 的调用位于 `MonsterShow_time_end` 及 `BOSSShow_time_end`。证据 L:36013–36025、127628–127654、127875–127898。

**推导。** 原图允许本波中途短暂超限，只要下一次开波检查前清到上限以内。不存在从首次超限起另倒数固定 3 秒/5 秒的脚本宽限。主线普通两波之间典型 50 秒，Boss入口54秒，Boss后82秒；剩余救场时间取决于当前波时间线，不能写固定 N 秒。

在开波函数中检查发生在生成新一波之前；同刻死亡和检查回调先后未实机核验。需要将此并入 Web 的最终统一事件排序裁决。

`OnePlayerFailed` 先更新记录、从 `Player_Index_Arr` 移除玩家；无人剩余时主线调用 `DefeatOfEveryOne`，无尽调用 `VictoryOfEveryOne` 进行成绩结算。多人时把失败玩家变为观战并处理其单位。单人 Web 可以显示“本局结束 + 无尽成绩”，不能把函数名 `VictoryOfEveryOne` 理解为打完全部无尽。证据 L:130291–130484。

### 3.3 登记与死亡清理顺序

`CreateDamageTrig(unit, portalId)` 为伤害登记触发器，寻找全局数组的首个空槽，写入 `mon_arr`、路径索引、伤害触发器数组，再加入对应个人数组。字节码 `B:main/f294/f36` 已核对空槽循环。L:129643–129700 的反编译 `while nil` 不可信。

死亡事件先处理深渊 Boss 回调（`Game_Mode==2`），然后对 `mBOS` 累加 `Kill_Boss_Num` 并在达到活动玩家数时提前结算，再处理挑战 Boss 奖励，随后调用 `DeadToRemoveUnitAndTrig` 清除登记。该清理会从 `mon_arr` 和对应个人数组移除单位、将路径索引置 -1、销毁伤害触发器。证据 L:115916–115969、29729–29800。因此死尸外观是否仍在场不应影响下一次容怪点数。

`ClearAllMon` 直接 `RemoveUnit` 后重建全局/个人怪物数组（L:129883–129913）。它不等价于批量击杀，不应凭空给击杀奖励。

## 4. 难度与透支的乘区

### 4.1 主线基础缩放

`GetGameLvFlag()` 返回简单 0.8、普通 1.2、困难 1.62、噩梦 2.5、地狱 2.6。主线出怪将 **最大法力** 乘难度并补满，生命另乘难度与透支生命因子并补满；护甲不普遍乘难度。证据 L:126896–126927、128711–128871。

设 D 为难度倍率，H0/M0/A0 为对象基础生命/法力/护甲，p 为已经在 `J100_Remove` 生效的透支点：

- 普通主线怪：`H=H0*D*(1+0.2p)`；`M=M0*D`；p>0 时 `armor=A0*(1+0.02p)`，增加 T202 能力，等级 p。
- `UnitIsHero(unit)` 判为 Boss 且非挑战店 Boss：`H=H0*D*(1+0.1p)`；p>0 时 `armor=A0*(1+0.01p)`，T202 等级 `floor(p/3)`。
- 挑战店 Boss 分支在这个生成函数内令生命透支因子为 1；其专用生成流程另查挑战规则。

证据 L:128735–128852，透支累计与 getter L:61073–61117、61167–61180、61308–61339。**`UnitIsHero(u)` 的准确谓词是 `GetUnitAbilityLevel(u,'N534') > 0 AND IsUnitType(u,UNIT_TYPE_SAPPER)`**，由 `B:main/f7/f45`（反汇编52445起）复核，L:32149–32163 的反编译失真。与对象 `UnitAbilities.abilList`、`UnitBalance.type` 联查，主线5/10/…/50及肉山成立，其他主线普通怪不成立；无尽mw11–mw17成立，mw01–mw04不成立（mw04虽有N534，但没有sapper）。不能直接用原生英雄类型、只检测N534或名字含“Boss”替代。T202 的伤害减免公式由战斗规则闭合。

### 4.2 透支何时生效

原图 11/16/21/26/31/36/41/46 波开放 J100，12/17/22/27/32/37/42/47 波调用 `J100_Remove` 收口。点击 J100 立刻使总点数 +1、待生效生命累计值 +0.2、福利伤害收益因子 +0.08、待生效护甲累计 +0.02、待生效减伤层数 +1；**怪物生命/护甲/减伤在下一次 `J100_Remove` 才复制到生效数组**。福利收益因子直接使用累计数组。总点数硬上限20，原平台地图等级上限已由主设计决定移除，此处只保留原证据。证据 L:128347–128400、61016–61115、61167–61180。

最终肉山出现前调用 `J100_Reset_Monster_Addition`：重置怪物生命/减伤/护甲数组并移除透支操作，不清空已得到的 `J100_TouZhiDian_Arr` 成绩加成。证据 L:127902–127908、61223–61307。

## 5. 福利打金

触发波：5/10/15/20/25/30/35/40/45/50，以及54。每波开波后40秒调用 `MoneyShow_showDialog`，再等10秒进入福利；持续20秒。在福利开始时每活动口安排 t=0 和 t=0.95 两次 `Trig_MoneyShow`，分别生成 m999、m998，生命/法力分别设 `cur_monLv*3800` / `cur_monLv*200`。证据 L:129733–129763、126784–126811、126930–126978、127513–127611。

福利结束先 `KillUnit` 尚存 m999/m998，再结算并归零 `Money_Damage_Sum`。证据 L:127240–127395。福利怪伤害回调会记账后把实际事件伤害置0，不是简单“打死一只固定奖金”；原脚本对物理/法术等有专门折算（L:114376–114474），须与战斗文档提供的最终福利记账伤害相接。

**个人模式精确结算公式。** 对每位记账伤害 S>0 的玩家，令 `X=S*J100_Get_Money_Addition(playerIndex)`，即已累计的 `1+0.08*透支点`；n 为当前主线波：

```
q(n) = 0.55,0.50,0.45,0.40,0.34,0.28,0.22,0.16,0.12,0.08,0.04
       对应 n<6,<11,<16,<21,<26,<31,<36,<41,<46,<51,<56
C = 1000 + 2000*(n/5-1)^2
G = floor(X/23*q(n)) + (1-C/(C+X))*n*180
按顺序执行（后项使用前项已修改后的 G）：
 if G> 50000: G= 50000+(G- 50000)*0.60
 if G>100000: G=100000+(G-100000)*0.30
 if G>150000: G=150000+(G-150000)*0.10
 if G>200000: G=200000+(G-200000)*0.03
 if G>300000: G=300000+(G-300000)*0.01
G = floor(G*VIP因子)
```

VIP因子默认1，共享VIP开启1.05，玩家同时持有SHOPITEM08和SHOPITEM01则覆盖为1.15。**按 Q18，Web 此处采用 1.15，仍遵循上面分段计算和取整顺序。** 不能把多个阈值公式分别对原始 G 求后相加，也不能把透支直接当“最终金币×1.08”。证据 L:127205–127239、127280–127395；发放 L:127438–127452。个人打金最高记录还有单人额外条件，归持久化规则。

团队结算是另一套有理式（L:127050–127160）：`X` 同上，`C1=140000+260000*(n/5-1)^2`，`C2=2000+2000*(n/5-1)^2`，未加VIP前 `G=(1-C1/(C1+X))*n*2000+(1-C2/(C2+X))*n*200`。Web已决定统一个人模式，所有难度使用前述个人公式；团队公式仅作为原图分支证据。

## 6. 肉山与进入后续模式

### 6.1 数量、属性、截止

肉山开波再次做容怪检查，设置 `cur_monLv=55`，登记480秒 `BossStopTimer`，重置透支怪物加成，每活动口创建一只 `mBOS`。无周期肉山刷新。证据 L:127864–127927、128897–128923。

设活动玩家数 N、难度 D，重置透支后：

```
肉山最大生命 = 3,000,000*D - (4-N)*600,000*D
肉山护甲 = 1000 - (4-N)*130*D
肉山最大法力 = 300,000*D
```

单人生命为 `1,200,000*D`，护甲为 `1000-390*D`。这里护甲扣减包含 D，但基础1000没有乘 D，不能简化为 `(1000-390)*D`。证据 L:128846–128889，基础对象 `units_unitbalance.json` 的 `unitBalanceID=mBOS`。

### 6.2 结算条件（字节码已复核）

`BOSS_Over_Hander` 被480秒到期触发，或在累计击杀肉山数达到活动玩家数时提前触发（L:115930–115945）。它销毁计时器/界面并 `ClearAllMon`，然后判断：

```
if Kill_Boss_Num > 0 and GAME_MODE_CHOOSE != 0:
    每名玩家 +8000*Kill_Boss_Num 金币
    5秒后进入已选的后续模式
else:
    VictoryOfEveryOne()  # 主线结算，不开放后续
```

**零击杀超时也是主线“胜利结算”函数路径，并非 Defeat。** 这一不直观结果已用 `B:main/f294/f33` 的 `lt k6,r0`、`eq k6,r0` 与 `l133` 分支复核；不是反编译结构推断。图鉴仅规定至少一只才能进入后续，没有给出相反的零击杀结算规则，按“缺失由原图补全”的既定原则保留该路径。原提示“仅限噩梦以上”陈旧；实际困难也允许无尽，图鉴 `玩法总览!B13` 与实际难度选择器一致。

## 7. 无尽

### 7.1 进入与跳波

肉山结算后5秒进入 `Game_Mode=1`，再6秒显示规则，再15秒开启选择窗；选择窗15秒，超时未投完按1波。可选1/50/100/150/200/250，取最低票；单人直接取自己的票。选完设置 `cur_endless_lv=start-1`，20秒后 `EndLessComing`，再经 `MonsterShow_showDialog` 倒计时后首次开波。证据 L:128925–129423，其中选择结束 L:128955–128974，默认超时 L:129151–129177，选择窗 L:129180–129326，入口 L:129333–129423。

首次 start=1 时 `cur_endless_lv=0`，倒计时1秒；跳到50/100/…时前置值为49/99/…，按普通无尽倒计时14秒。故选择结束至首波分别21秒或34秒。这是 `MonsterShow_showDialog` 依据当前（上一波）是否Boss选择倒计时的推导，证据 L:126716–126742。

跳波给 i329 无尽魔石数量 3/7/11/15/19（对应50/100/150/200/250）；木材等于魔石数量×100，即300/700/1100/1500/1900。证据 L:128975–129045。非1起始时，要在开波流程中到达 `start+10` 才保存无尽层数；存档发生在生成该波之前，不应把提示“通过60波”误读为清空60波。证据 L:127780–127829。

### 7.2 刷新和容怪节奏

正常非比赛模式，每个无尽波开波时抽一次 `endlessType`。10的倍数波从1–7整数均匀抽取，对应 mw11…mw17；其余从1–4抽取，对应 mw01…mw04。所有本波批次用相同类型。证据 L:127736–127778、128447–128468。

普通波：立即一批，随后每2秒一批，14秒停止；数学末批t=14与停止同秒，所以每口 **7–8只、14–16格**，待 native 排序核验。Boss波：立即一批后从 `Trig_monsterShow` 返回，无周期批次，10秒时停止空触发器。证据 `B:main/f294/f17`、L:126677–126682、129774–129797。

下波准备从本波开波后1秒启动，其倒计时取本波类型：普通后14秒，Boss后10秒。因此普通开波到下波开波15秒、Boss到下波11秒；下波开波前先做容怪检查，再 `cur_endless_lv += 1`。证据 L:129714–129733、126716–126742、127628–127662。

个人无尽用仍活动的 `Player_Index_Arr`；只有团队无尽用第22波锁定的 `Player_Index_Arr_Lock`。这是字节码 `B:main/f294/f16` 的明确 AND 条件，反编译器错排了 else。

### 7.3 非比赛个人无尽的成长

设 e 为当前无尽波号（不是主线55以后相加）：

|类别|最大生命|最大法力|护甲|
|---|---|---|---|
|普通|`5000+6600e`|`800+1000e`|`min(500,48+1.5e)`|
|Boss（原 UnitIsHero 判定）|`5000+14400e`|`800+4000e`|`min(700,98+1.5e)`|

Boss个人分支把基础生命线性系数18000乘0.8，额外挂N508。团队公式对生命/法力线性系数另乘 `1.5-0.1*活动玩家数`；注意其提示写“100-人数×10%”，与实际系数不一致。比赛模式另有×7系数和10倍护甲斜率，不默认纳入普通模式。证据 L:128578–128711。

无尽还有全局伤害倍率，不可只增长HP：

```
R(e) = 100-0.3156e                     e <= 300
       5.32-0.14*(e-300)               e > 300
若 e>338 或 R<0.01，则 R=0.01
```

不是达到338就结束；338之后继续但倍率下限0.01。伤害回调将此 `R/100` 与伤害类别因子相乘：物理1.8、法术3.2、其他1.2；带T176的目标还有 `min(2.5,100/R)` 修正，来源q025有例外。证据 L:127696–127718、110100–110103、114155–114218。最终作用顺序由战斗规则文档统筹，别再把它当护甲或减伤百分比重复应用。 **Web已由末日Q67覆盖T176这一项**：无尽减伤率减半，即剩余承伤比例由r变成`1−(1−r)/2`；类型倍率、无标记和q025例外不改。旧min公式仅是来源证据，见[末日](doom.md)。

## 8. 深渊

### 8.1 入口、选英雄、时间

肉山结算后5秒令 `Game_Mode=2` 并调用 `Abyss_Init`；再30秒调用 `Abyss_Start_New_Turn`。该函数先关次+1、给工人J003解放英雄、刷新神秘店，登记 **240秒准备期**。所有活动玩家都选好一个英雄时 `J003_Action` 立即调用 `StartHander1`，跳过剩余准备。不是函数里未使用的局部值20秒。证据 L:129403–129415、107228–107233、107154、109062–109183、37186–37194。

准备结束后5秒Boss出现（L:108851–108870）。没选英雄的玩家由 `StartHander1` 枚举其英雄取第一个合适对象；枚举顺序依赖原引擎，本轮不推定最强/最早建造。它隐藏其他单位并保存位置/所有权，出战英雄取消T033、增加P100、修改移动类型；回合结算恢复。证据 L:108695–109035、107995–108087。

|关次|对象|初始战斗时限|规则|
|---:|---|---:|---|
|1|ma01 金币小鸡|60秒|伤害记账但实际伤害置0，时间到正常转关，不扣重试|
|2|ma03 全能骑士|150秒|击杀掉落i800；成功结算给每工人i237|
|3|ma06 遗忘法师|150秒|成功结算给每工人i237|
|4|ma99 深渊巨龙|150秒|同关连续复生、层计数递增，详见下节|

表来自 `Abyss_Desc` 初始化 L:107055–107115；时限实际 `TimerStart` 使用 desc[3]，L:108512–108553。入场人数生命系数 `F=1-0.2*(4-N)` 在 `Abyss_Init` 取当时活动人数，单人为0.4（L:107253–107262）。前3关使用对象基础HP×F；不再乘主线难度D。对象ma03基础1500000、ma06基础2000000，单人分别600000/800000。证据 L:107705–107755及单位平衡JSON。

小鸡伤害>50且 `GetRandomInt(1,100)<12` 会在附近掉i421，整数概率11%；0.8秒一次解除暂停/负面等；奖励拾取细节归物品规则。该段非图鉴明确概率，所以记录原式不自行改成12%。证据 L:107468–107503、107821–107834。

### 8.2 失败重试（字节码复核）

共享剩余重试计数初始化4，整个深渊过程中共用，不在每关重置。时限到时结算函数 L28_2 先销毁战斗/伤害/音乐计时器，恢复隐藏单位及英雄位置，清空选英雄集合。

- 第1关特殊：清掉小鸡及其未拾取奖励，直接成功流程。
- 其他关Boss仍活着：若剩余重试>0，显示剩余次数、减1、`Abyss_Cur_Lv -= 1`，把Boss剩余HP存入L4_2，清怪，8秒后重新 `Abyss_Start_New_Turn`（再+1返回同关），再经历240秒可跳过准备和5秒出场。重试出生先算最大HP，再恢复上次剩余HP。
- 剩余重试=0且仍失败：`DefeatOfEveryOne`。因此是首次尝试+4次重试，第5次失败终止，符合提示“5次失败机会”，不是5次重试。
- 成功时清掉残怪，L4_2归0、奖励，然后8秒后下一关。

证据 L:107150、107957–108169、107799–107805；`B:main/f290/f11` 已核对失败分支（反汇编158685–158755）。Boss死亡与时限同刻的先后仍待验证，不以两者都调用为由发两次奖励。

### 8.3 巨龙层、复生与奖励

`Abyss_Cur_Rank_Lv` 初始 **0**；进入第4关并未改为1。最大生命公式 `floor(400000*1.2^((rank+1)*0.5))*F`，最大法力 `(rank+1)*5000`，初次给满；重试可继承剩余HP。证据 L:107139、107151、107680–107698、107755–107805。

当当前 `Abyss_BOSS` 被杀且不处于复生保护L19_2时，若 `Abyss_Cur_Lv==#Abyss_Desc`（4）：

1. 标记复生保护；先 `Abyss_Save_Player_Data()` 保存**击杀前 rank**，然后 rank+1。
2. 在死去Boss的位置创建新ma99，隐藏旧Boss，保留路径用户数据；增加N560并holdposition。
3. 2秒后进入动画处理，再5.5秒后加N561，再2秒后恢复战斗，合计 **9.5秒复生演出**。演出期间旧战斗计时器被销毁，不消耗战斗余额。
4. 新倒计时时间 `min(300, oldRemaining+30)`；重新计算HP/法力、去Avul、按层升级技能并注册伤害触发器；从复生完成开始计时。

证据 L:108281–108487，`Abyss_Unit_Dead` 的 `B:main/f290/f17` 可复查。它没有走普通成功回合的L27_2礼包结算，所以**不是每杀一层巨龙就重新选英雄或发i237**；原明确奖励是+30秒、层数记录及特定物品掉落（第4关掉落字段空）。

原存档把 `Abyss_Cur_Rank_Lv` 直接写入 `abyssNewN`（L:109279–109340）。因此首只巨龙被杀保存0、下一只显示rank1。这是已读赋值顺序形成的**零基层号**，与“第4关开始计层”不构成明确数值冲突，按原图保留；如果界面额外展示已击杀只数，必须另计而不能悄悄给原存档rank加1。

巨龙技能等级：N566随rank上限20；后续N562/N563/N564/N568按rank阈值逐步升级，完整技能映射归战斗表。巨龙幼龙每个存活者使受到伤害再乘 `(1-0.01*活幼龙数)`，最低0，证据 L:107509–107539。第一轮与复生时的native最低技能等级行为（rank=0传入等级0）尚未运行验证。
