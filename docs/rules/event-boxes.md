# 三种活动礼盒：奖励、共用计数与扣费

本批仅闭合 `y005_Action`（圣诞袜）、`y007_Action`（元旦礼盒）、`y009_Action`（十一礼盒）及其直接入口和存档回调，不扩展其他活动。机器表见 [event-boxes-data.json](event-boxes-data.json)。关键分支已对照 `main.disasm`；下述百分比按 `GetRandomInt(a,b)` 返回闭区间内均匀整数计算，不声称恢复了原生随机算法。

**已定 Web 行为：** Q19/Q20/Q21 已使这三个礼盒的全部永久候选处于已拥有状态。礼盒继续按原价兑换，并走原来的积分／碎片分支；不删除礼盒、不发无限活动积分、不免除兑换成本。永久开放表示拥有相应权限，不表示自动给所有塔施加所有换皮效果。原版尚未拥有时的奖池和概率仍完整保留，便于核对；原生消费和持久化的 Web 选择单列在末尾。

## 共有算法与计数

三种礼盒读取同一玩家字段 `OpenGiftNum`，不是各自的计数。每次先读取旧值 `c`；只有当前礼盒仍有未拥有的永久候选时，才用旧值选阈值并把存档计数加 1。之后始终抽一次整数 `r = GetRandomInt(1,100)`，以 **`r < threshold`** 命中永久奖励，不能改成 `<=`。命中时先清零共用计数，再调用永久奖励助手；普通积分／碎片结果不清零。因此一种礼盒的未中奖次数会影响另外两种的下一次概率；已拥有全部对应奖励的礼盒不会给其他盒子增加计数。[读取 L34214](../../reference/map-6.25/main.readable.lua#L34214)、[递增 L35501](../../reference/map-6.25/main.readable.lua#L35501)、[重置 L35579](../../reference/map-6.25/main.readable.lua#L35579)。

所有未命中稀有奖励的开盒，再抽独立整数 `q = GetRandomInt(1,100)`：`q=1…49` 给皮肤碎片，`q=50…100` 给普通积分，随后再抽一次奖励数量。稀有奖励与货币奖励互斥。以下“49%／51%”是**已进入货币分支后的比例**；仍有稀有奖励时，完整概率须分别乘 `1-pRare`。已全拥有时 `pRare=0`，该比例就是每次开盒的最终比例。

调用顺序也需保留：圣诞／元旦命中稀有时只有 1 次随机调用；十一命中稀有时有 2 次（第二次选候选索引）；货币分支有 3 次。即使全拥有导致阈值 0，第一下无效的稀有判定随机数仍然会被抽取，不能在要求复现随机状态时直接略过。

## 充能、存档与错误反馈

三件可用物品在可叠加清单中；拾取新一份时，若槽 0–5 已有同 ID 的另一实例，就把充能数相加并删除新实例。`HasItem` 明确排除本次被拾取物品，不会把物品与自身合并。三者不互相合并。[清单 L95442](../../reference/map-6.25/main.readable.lua#L95442)、[查找 L96431](../../reference/map-6.25/main.readable.lua#L96431)、[合并 L97106](../../reference/map-6.25/main.readable.lua#L97106)；字节码 [L145278–145308](../../reference/map-6.25/main.disasm#L145278)。

物品表写 `uses=1, perishable=1, usable=1`。使用分支没有手动删除或减少充能，实际原生事件的消费时点不能从 Lua 函数本身证明。三个能力的 `Cool1=1`；`y006/y008` 的物品 `cooldownID` 都是 `I007`，`y010` 为 `I009`。[物品表 L15500](../../reference/map-6.25/units_itemdata.json#L15500)、[L15540](../../reference/map-6.25/units_itemdata.json#L15540)、[L15580](../../reference/map-6.25/units_itemdata.json#L15580)、[能力表 L20692](../../reference/map-6.25/units_abilitydata.json#L20692)。

`OpenGiftNum` 与 `ActScore0` 从平台账户分别载入，更新函数修改内存后触发各自保存。保存回调在 `isSuccessLoad==0` 时直接返回，不检查远端写入成功回执。碎片更新立即触发 `SkinPiece` 保存；礼盒普通积分更新只改 `score`，该函数内没有立即保存信号，通常的玩家数据保存会写 `score+scoreNew`。因此不能把原图脚本认作一个跨字段原子存档事务。[JASS L728–736](../../reference/map-6.25/war3map.j#L728)、[L1183](../../reference/map-6.25/war3map.j#L1183)、[L1228](../../reference/map-6.25/war3map.j#L1228)、[L1133](../../reference/map-6.25/war3map.j#L1133)、[L1362–1382](../../reference/map-6.25/war3map.j#L1362)；[Lua L33411](../../reference/map-6.25/main.readable.lua#L33411)、[L35643](../../reference/map-6.25/main.readable.lua#L35643)。

原版稀有奖励调用 `DZAPI_Score_Buy_Forever_item(player,0,skinAbility)`：先尝试在第一个可容纳的 `ScoreSkin` 字符串段尾添加 `,索引`，追加后长度必须 `<=50`；遇到不存在的下一段则失败。成功才扣普通积分 0 并加解锁科技；失败只显示“存档失败，积分归还”。但礼盒调用方已先清零计数，不接收成功结果，仍公告获得皮肤，不发补偿货币，也不退之前购买礼盒的 100 `ActScore`。这是真实已核的调用顺序，不代表观察过远端故障；全永久开放后这条稀有发奖失败路径不再可达。[Lua L34430](../../reference/map-6.25/main.readable.lua#L34430)、[L34538](../../reference/map-6.25/main.readable.lua#L34538)；字节码 `main/f8/f35` [L55994](../../reference/map-6.25/main.disasm#L55994)、`main/f8/f37` [L56168](../../reference/map-6.25/main.disasm#L56168)。

另一处反编译校正：`DZAPI_Has_Model` 对没有对应科技等级的项目返回字面 `false`；可读 Lua 错位的 `else` 看起来像可能返回 `nil`，字节码实际将映射不存在或科技等级 `<=0` 都跳到 `l18` 返回 `false`。因此“只将 ==false 的项目加入候选池”确实能纳入未拥有项目。[字节码 L55954–55992](../../reference/map-6.25/main.disasm#L55954)。

## Q24 下明确的 Web 基准与剩余边界

以下是 **Web 选择**，不冒充原客户端实测：

- 一次有效激活产生一次奖励并消耗 1 充能，充能归零移除物品。按载体和 `cooldownID` 计 1 秒冷却，圣诞／元旦共享，十一独立；冷却中或无充能的操作不发奖、不消耗、不取随机数。
- 兑换的活动积分扣减与生成／交付礼盒一并持久化；开盒的充能、奖励、计数、冷却与随机状态一并持久化。本机写入失败则这一操作都不提交，也不显示成功。它修正平台存档缺乏统一成功回执的边界，不改变已核的价格、奖池或概率。

仍需明确的原生边界只有以下直接相关项；本批不对它们虚构已闭合结论：

1. **底层 `AIfs` 的召唤参数缺省值。** `I007/I008/I009` 均 `code=AIfs`，明确保留 `DataC1=nsce, DataD1=nsca, Area1=200, BuffID1=BFig, Dur1=120, HeroDur1=60`，却没有 `DataA1/DataB1/UnitID1` 单元，也没有 `.w3a` 中这些 ID 的覆写；基础 `AIfs` 行则有 `DataA1=4, DataB1=4`。能力名字带“无用”只是说明文本，不能证明不会召唤。尚未确证自定义 SLK 的空数量在原引擎是 0 还是继承缺省，故既不能直接添加“4+4”召唤，也不能据此删除对象表中的召唤关联。本批未为该副作用制定 Web 裁决。[基础行 L3604](../../reference/map-6.25/units_abilitydata.json#L3604)、[礼盒行 L20692](../../reference/map-6.25/units_abilitydata.json#L20692)、[原始 SLK L18707–18748](../../reference/map-6.25/units_abilitydata.slk#L18707)、[能力名 L11318](../../reference/map-6.25/units_campaignabilitystrings.txt#L11318)。
2. **原生商店默认价格和满背包交付。** 六个物品行未列 `goldcost/lumbercost`，脚本只明确扣 100 `ActScore`；原生空字段默认值、`UnitAddItem` 失败后具体落地行为未实测。不得擅自额外收金币／木材，也不能把未列字段当成已验证的原客户端值。本批没有给满背包额外加退款或拒购规则。[物品表 L15479–15597](../../reference/map-6.25/units_itemdata.json#L15479)。

本批未发现需要推翻 Q19/Q20/Q21 的新冲突。49% 上限、49/51 货币分支及共用计数均是已核源码事实；不能仅因其不符合“50%”直觉而改概率。未扩大调查活动积分全部赚取来源、其他节日箱子或任务链。
